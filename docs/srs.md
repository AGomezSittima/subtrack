# Subtrack — Software Requirements Specification (SRS)

Nov 10, 2026 · @Alvaro

## Introduction

This SRS specifies **what** Subtrack does. **How** it is built (stack, schema, API, deployment) is in the SDD: Subtrack — Software Design Description (SDD).

Subtrack is a local, single-user app to track subscriptions, record their payments, get reminded before renewals and see cost statistics. It is also a learning project: the same requirements are implemented by two interchangeable backends.

### Definitions

| Term | Meaning |
| --- | --- |
| Subscription | A recurring charge for a service, e.g. Spotify Premium |
| Billing interval | A count and a unit (day, week, month, year): "every 3 months" |
| Anchor date | The first billing date; all later billing dates derive from it |
| Expected payment | A billing date generated from the schedule, not yet confirmed |
| Monthly equivalent | The cost of a subscription spread over one month, whatever its interval |
| Backfill | Recording past billing dates as already paid when adding an existing subscription |
| Ends on | The last day of access of a cancelled subscription; no payments on or after it |
| Archive | Hide a subscription from lists, totals and reminders while keeping its payment history |
| Passcode | Optional secret that locks the app; it protects against someone using an open computer, not against reading the data file |

## Overall description

**User.** One person, on their own computer. There are no accounts and no sharing.

**Constraints**

- Single user, no accounts. An optional passcode can lock the app (FR-40 to FR-45).
- One currency: euros.
- Runs locally as a container stack the user starts and stops at will.
- Two backend implementations must behave identically (NFR-6).

**Assumptions.** The computer is often off or the app stopped; nothing may be lost while it is down (BR-19). The host disk is encrypted (e.g. FileVault, BitLocker, LUKS); the app does not encrypt its own data.

**Goals**

1. Know at any time what you pay per month and per year, and what is due next.
2. Keep an accurate record of what was actually paid, including price changes.
3. Compare two backend stacks on identical requirements and identical tests.

## Functional requirements

IDs (FR-x) are meant to be referenced from tests and commits in both backends.

### Subscriptions

- **FR-1** Create, edit and delete a subscription: name, category, plan name, price, billing interval (count + unit: day, week, month, year), anchor date, optional trial end date, payment method label, website, cancel URL, notes.
- **FR-2** Pick the service from a catalogue to prefill name, category, website and logo; free text is always allowed.
- **FR-3** Change status: trial, active, paused, cancelled. Cancelling records the cancellation date and an access end date (ends on), which can be a year or more later (e.g. a yearly Proton plan cancelled early); the subscription shows "Ends on \<date>" until then. Paused subscriptions generate no payments or renewal reminders while paused.
- **FR-4** Show the next renewal date and the monthly-equivalent cost for each subscription.
- **FR-5** List subscriptions with filter (status, category) and sort (next renewal, cost, name).
- **FR-27** When a new subscription's anchor date is in the past, the user can choose to backfill: every past billing date is recorded as paid at the price in force, so history and statistics start complete.
- **FR-28** Archive a subscription: it disappears from lists, totals and reminders, but its payments stay in spending history. Archived subscriptions can be listed and restored.
- **FR-29** Deleting a subscription first shows a warning with how many payments and how much past spend will disappear from history, and offers to archive instead.
- **FR-46** When the payment method label or the notes look like sensitive data (a full card number or an IBAN), the form shows a warning recommending a short label such as "Visa ··4417". The warning does not block saving.

### Price history

- **FR-6** Changing the price asks for an effective date and stores a price-history entry instead of overwriting.
- **FR-7** Expected payments due on or after the effective date use the new price.

### Payments

- **FR-8** The app generates expected payments from each active subscription's schedule, up to a configurable horizon (default 60 days ahead).
- **FR-9** Confirm an expected payment as paid, with an optional different amount and paid date; mark it skipped or failed; add a note.
- **FR-10** When a confirmed amount differs from the current price, offer to record a price change.
- **FR-11** Optional per-subscription auto-confirm: expected payments become paid on their due date.
- **FR-12** Record a one-off manual payment not generated by the schedule.
- **FR-13** Payment list per subscription and globally, filterable by status and date range.

### Reminders and notifications

- **FR-14** A global default reminder (N days before each renewal, default 3).
- **FR-15** Per-subscription override: different lead days, or off.
- **FR-16** Built-in events: trial ending (default 3 days before), yearly renewal (default 14 days before), payment still expected after its due date (overdue), cancelled subscription about to end (default 7 days before, and on the end date).
- **FR-17** Notifications appear in an in-app list with an unread badge; mark one or all as read; open the related subscription or payment. Each notification has a severity (info, warning, critical) shown by color and icon.
- **FR-18** Notifications exist only inside the app. There is no email, push or phone channel, by decision.
- **FR-30** When the app is opened and the catch-up has run, a "While you were away" summary lists every new notification, grouped as ending soon, overdue and renewing soon. It stays until the user dismisses it.
- **FR-31** Ending-soon and overdue items stay pinned at the top of the dashboard until resolved (payment confirmed, skipped or failed; subscription ended or reactivated).

### Statistics

- **FR-19** Totals: monthly-equivalent and yearly-equivalent cost of subscriptions that will be charged again; archived subscriptions never count.
- **FR-20** Breakdown by category and by payment method.
- **FR-21** Upcoming payments in the next 7 and 30 days, with total.
- **FR-22** Spend over time by month: actual (paid) for the past, projected (expected) for the coming months.
- **FR-23** Planned vs actual per month, and count of skipped/failed payments.
- **FR-24** Yearly vs monthly comparison when a subscription's catalogue entry lists both plans.

### Data

- **FR-25** Export all data as JSON and CSV; import from the same JSON format.
- **FR-26** One settings page groups every setting: appearance, language and region, reminders, payments, logos, privacy lock, and data (export/import).

### Localization

- **FR-32** The UI is available in English and Spanish, switchable in settings; the default follows the browser language.
- **FR-33** Dates, numbers and amounts are formatted for the selected language (11,99 € in Spanish, €11.99 in English). The currency is always EUR.
- **FR-34** All user-facing text is translated, including notifications and error messages.

### Appearance and region

- **FR-35** Theme: light, dark, or follow the system (default).
- **FR-36** Font size: small, default or large. The whole interface scales with it, not only text.
- **FR-37** Reduced motion: follow the system (default), or always reduce.
- **FR-38** First day of the week, used by date pickers and calendar views (default Monday).
- **FR-39** Appearance settings apply immediately and are the same in any browser.

### Privacy lock

The privacy lock stops casual use of the app by someone at a computer that is already logged in. It does not protect the data file itself: that relies on the operating system's screen lock and disk encryption (see Assumptions). The UI calls it a privacy lock and does not describe it as encryption or data protection.

- **FR-40** Optional alphanumeric passcode of at least 6 characters, off by default.
- **FR-41** Lock policy, when a passcode is set: on every open of the app, after 5, 15, 30 or 60 minutes without user activity, or manual only. Default: after 15 minutes. Background activity (such as checking for new notifications) does not count as user activity.
- **FR-42** A "Lock now" button is always available while a passcode is set.
- **FR-43** While locked, the app shows only a full lock screen: no subscription data, totals, names, notifications or counts. Data is also unreachable through the API.
- **FR-44** After 5 wrong attempts, each further attempt is delayed, doubling up to 15 minutes. A correct passcode resets the counter.
- **FR-45** Changing or removing the passcode requires the current one. A forgotten passcode can be removed only with a command run on the machine hosting the app.

## Domain concepts

The information the system keeps, independent of how it is stored (the schema is in the SDD).

| Concept | Information |
| --- | --- |
| Catalogue service | Name, website domain, category, typical plans with price and interval |
| Subscription | Service, category, plan, current price, billing interval, anchor date, status, trial end, cancellation date, ends on, pause date, archived, payment method label, auto-confirm, reminder override, website, cancel link, notes |
| Price change | New price and the date it takes effect |
| Payment | Due date, expected amount, paid amount and date, status (expected, paid, skipped, failed), origin (scheduled, backfill, manual), note |
| Notification | Type, severity, related subscription or payment, message parameters (the text is rendered in the user's language), date it fired, read or unread |
| Settings | Reminder defaults, payment horizon, logo service key, language, theme, font size, reduced motion, first day of week, passcode (stored only in a form that cannot be reversed), lock policy |

### Initial catalogue

The catalogue ships with mainstream services, starting with: Cloudflare Domains, Spotify, Bitwarden, Proton VPN, Claude (Anthropic), ChatGPT (OpenAI), and similar. Plans and prices per service are still to be researched (see open questions).

## Business rules

These rules are the shared core of both backends. Each one becomes a test case that both must pass with identical results.

### Renewal dates

- **BR-1** The n-th billing date is always computed from the anchor date: `anchor + n × interval`, never from the previous billing date. This avoids drift (31st → 28th → 28th forever).
- **BR-2** If the target month is shorter than the anchor day, clamp to the last day of that month.
- **BR-3** All dates are local dates in Europe/Madrid; no times of day are stored for billing.

| Anchor | Interval | Next dates | Rule |
| --- | --- | --- | --- |
| 2026-01-31 | 1 month | 2026-02-28, 2026-03-31, 2026-04-30 | BR-1, BR-2 |
| 2026-01-31 | 3 months | 2026-04-30, 2026-07-31, 2026-10-31 | BR-1, BR-2 |
| 2024-02-29 | 1 year | 2025-02-28, 2026-02-28, 2028-02-29 | BR-1, BR-2 |
| 2026-11-10 | 1 week | 2026-11-17, 2026-11-24 | BR-1 |
| 2026-11-10 | 14 days | 2026-11-24, 2026-12-08 | BR-1 |

### Cost normalization

- **BR-4** Monthly equivalent = price ÷ interval in months, where 1 year = 12 months; weekly plans charge 52/12 times a month and daily plans 365/12 times. Compute exactly, round half-up to cents only for display and totals.
- **BR-5** Yearly equivalent = monthly equivalent × 12.
- **BR-22** Derived values (monthly and yearly equivalents, and their totals) are computed exactly and rounded once, half-up to the cent, only at the end. A derived value is never computed from another rounded value: the yearly equivalent is the exact monthly × 12, rounded once.
- **BR-25** Sums of prices and recorded payments (spend per month, total paid) are whole cents and are never rounded.
- **BR-26** When parts must add up to a shown total (category breakdown, charts), parts are allocated by largest remainder: round every part down, then give the leftover cents one by one to the parts with the largest remainders. Example: three weekly plans at 2.99 € are 12.9567 € each; the total is 38.87 € and the parts show 12.96 €, 12.96 € and 12.95 €.

| Price | Interval | Monthly equivalent |
| --- | --- | --- |
| 11.99 € | 1 month | 11.99 € |
| 49.99 € | 1 year | 4.17 € |
| 14.99 € | 3 months | 5.00 € |
| 2.99 € | 1 week | 12.96 € |

### Payment generation

- **BR-6** For each active or trial subscription, create `expected` payments for every billing date from the anchor up to today + horizon. Billing dates before the subscription was created in the app are not generated unless the user asks for a backfill.
- **BR-7** Generation is idempotent: the unique key (subscription\_id, due\_date) means re-running it never duplicates.
- **BR-8** `expected_cents` = the price-history entry in force on the due date.
- **BR-9** A price change updates `expected_cents` on payments still `expected` with due\_date ≥ effective\_from. Paid, skipped and failed payments never change.
- **BR-10** Pausing or cancelling deletes scheduled payments still `expected` with due\_date after the pause date, or on or after ends\_on when cancelling. ends\_on defaults to the next billing date after cancellation and can be edited. Resuming regenerates payments from the anchor.
- **BR-11** With auto\_confirm on, an `expected` payment becomes `paid` on its due date with paid\_cents = expected\_cents.
- **BR-12** A trial subscription becomes active on the run after trial\_end\_date, unless cancelled first.

### Reminders

- **BR-13** For each upcoming `expected` payment, a renewal notification fires on due\_date − reminder\_days (subscription override, else global default). -1 means off.
- **BR-14** Yearly-or-longer intervals use `yearly_reminder_days` instead of the normal lead time.
- **BR-15** Trial ending fires on trial\_end\_date − `trial_reminder_days`.
- **BR-16** Overdue fires once, the day after due\_date, for a payment still `expected`.
- **BR-17** Every notification has a dedupe key (`type:subscription:date`). Creating it twice is a no-op.
- **BR-21** An overdue payment stays `expected` until the user confirms, skips or fails it. The app never changes its status on its own.
- **BR-23** An ending notification fires on ends\_on − `ending_reminder_days` (default 7) and again on ends\_on, for cancelled subscriptions only.
- **BR-24** Severity: overdue is critical; ending and trial ending are warning; renewal and yearly renewal are info.

### Scheduler and catch-up

- **BR-18** One job, run on backend startup and then every hour. Steps in order: activate ended trials, generate payments, auto-confirm, create notifications, store `last_scheduler_run`.
- **BR-19** Catch-up: notifications are created for every trigger date between `last_scheduler_run` and today, so reminders that fell while the containers were stopped still appear on the next start. Triggers whose payment is already paid or past are skipped, except overdue.
- **BR-20** The job is safe to run any number of times (BR-7, BR-17), so a restart mid-run is harmless.

## Non-functional requirements

| ID | Requirement |
| --- | --- |
| NFR-1 | Runs locally as a container stack; starting and stopping each take one command. |
| NFR-2 | Data persists across stops, restarts and rebuilds until the user deletes it. |
| NFR-3 | The app is not reachable from other machines, and the data store is not reachable from outside the stack. |
| NFR-4 | After start, the app is usable within 30 seconds on a typical laptop. |
| NFR-5 | Works in current desktop browsers and stays usable at phone width. |
| NFR-6 | Two backend implementations expose the same API, pass the same business-rule tests, and share data, so switching needs no migration. |
| NFR-7 | Amounts are exact to the cent; totals never drift from rounding. |
| NFR-8 | The server side makes no outbound network calls; only logos are loaded from the internet, by the browser. |
| NFR-9 | Stored dates and timestamps use one canonical ISO text format, whichever backend wrote them; data written by one backend reads identically in the other. |
| NFR-10 | Uses the latest stable versions of languages, frameworks and tools that are compatible with each other. |
| NFR-11 | The passcode is never stored, logged or returned in readable form. The lock is enforced by the server, not only hidden in the UI. |

## Out of scope and open questions

**Out of scope for v1:** user accounts and multiple users, encryption of the stored data, currencies other than EUR, email or push notifications, bank or card imports, receipt-email parsing, shared subscriptions split between people, budgets and spending limits. Services' own APIs are not used: none expose billing data to third parties.

**Decided on 2026-11-10**

| Question | Decision |
| --- | --- |
| Backfill past payments | Yes, optional per new subscription (FR-27) |
| Overdue payments | Stay expected until the user acts (BR-21) |
| Initial catalogue | Mainstream services, starting with the list under Initial catalogue |
| Frontend and logo provider | Design decisions, recorded in Subtrack — Software Design Description (SDD) |
| Cancelled but still active | Ends on date (FR-3, BR-10, BR-23) |
| Deleting a subscription | Warn and offer archive (FR-28, FR-29) |
| Rounding of totals | Round once at the end (BR-22) |
| Notification channels | In-app only, made prominent (FR-17, FR-30, FR-31) |
| UI language | English and Spanish (FR-32 to FR-34) |
| Settings page | Appearance, region and privacy lock added (FR-26, FR-35 to FR-45) |
